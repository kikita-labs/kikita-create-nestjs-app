# i18n

Present only because this project opted into multi-locale support. Delete this file (and its
`core/README.md` row / `AGENTS.md` bullet) if that questionnaire answer was "no".

`nestjs-i18n` — Nest has no built-in localization, this is the de facto library. Covers both
REST error/response messages and, if bot (or both) was chosen, bot reply translation via the
matching platform integration below.

## Translation files

`src/i18n/<locale>/<namespace>.json`, one folder per locale, one JSON file per logical group
(`errors.json`, `users.json`, ...) — not one giant file per locale. `DEFAULT_LOCALE` env var
sets the fallback (default `en`); every translation key must exist in the fallback locale even
if not yet translated elsewhere, so a missing key degrades to English instead of an empty string.

```json
// src/i18n/en/users.json
{ "notFound": "User not found" }
```

```ts
// core/i18n/i18n.module.ts
@Module({
  imports: [
    NestI18nModule.forRootAsync({
      inject: [ConfigService],
      useFactory: (configService: ConfigService) => ({
        fallbackLanguage: configService.getOrThrow<string>('DEFAULT_LOCALE'),
        loaderOptions: { path: path.join(__dirname, '../../i18n/'), watch: true },
      }),
      resolvers: [AcceptLanguageResolver], // REST-only, see below — bot resolves differently
    }),
  ],
})
export class I18nModule {}
```

## REST: locale resolution

`AcceptLanguageResolver`, not the raw `HeaderResolver` — `HeaderResolver` doesn't parse
`Accept-Language` per RFC 4647 (weighted `q=` values, wildcard ranges); `AcceptLanguageResolver`
does. Falls back to `fallbackLanguage` when the header is missing or requests a locale with no
translation file.

```ts
// modules/users/users.service.ts
throw new NotFoundException(this.i18n.t('users.notFound'));
```

**Validation error messages**: `class-validator` decorators take `i18nValidationMessage()`
instead of a hardcoded English string, and a global `I18nValidationExceptionFilter` (shipped by
`nestjs-i18n`) formats the `ValidationPipe`'s rejection in the resolved locale.

```ts
@IsEmail({}, { message: i18nValidationMessage('validation.isEmail') })
email!: string;
```

**Filter ordering**: `I18nValidationExceptionFilter` and `PrismaExceptionFilter`
(`../architecture/transport-adapter.md`) are both `APP_FILTER` providers — Nest runs filters in
reverse registration order (last registered, first tried), and each only handles the exception
types it recognizes, passing through anything else. Order doesn't matter for correctness here
since the two filters catch disjoint exception types (`ValidationError` vs
`PrismaClientKnownRequestError`) — just don't assume one supersedes the other if a third global
filter is added later without checking what it catches.

## Bot: locale resolution (platform-specific, not `AcceptLanguageResolver`)

A bot has no `Accept-Language` header — the platform's own per-user locale field is the source
of truth, resolved differently per platform:

<!-- SCAFFOLD: keep only if platform = Telegram -->
### Telegram

`nestjs-telegraf-i18n` merges `nestjs-telegraf`'s update context with `nestjs-i18n`, resolving
the locale from `ctx.from.language_code` (the user's Telegram client language, not something
they explicitly picked for this bot) automatically — no manual header parsing. Wiring it needs
three things in `bot/bot.module.ts`, not just installing the package:

```ts
// bot/bot.module.ts
@Module({
  imports: [
    TelegrafI18nModule, // 1. import alongside TelegrafModule
    TelegrafModule.forRootAsync({
      inject: [ConfigService, TelegrafI18nMiddlewareProvider],
      useFactory: (configService: ConfigService, telegrafI18n: TelegrafI18nMiddlewareProvider) => ({
        token: configService.getOrThrow<string>('TELEGRAM_BOT_TOKEN'),
        options: { contextType: TelegrafI18nContext }, // 2. custom context type
        middlewares: [
          (ctx: Context, next: () => Promise<void>) => telegrafI18n.telegrafI18nMiddleware(ctx, next),
        ], // 3. middleware wired in
      }),
    }),
  ],
})
export class BotModule {}
```

Update handlers then take `@Ctx() ctx: TelegrafI18nContext` (not the plain `Context` from the
generic pattern above) to get `ctx.t('key')`/`ctx.tReply('key')`.

<!-- SCAFFOLD: keep only if platform = Discord -->
### Discord

`@necord/localization` reads the interaction's own `locale` field (Discord sends this on every
interaction, reflecting the user's Discord client language) and wires it into slash-command
descriptions and reply translation.

<!-- SCAFFOLD: keep only if platform = "another platform" -->
### {{BOT_PLATFORM}}

No prewritten i18n integration ships for this platform. Resolve the user's locale from whatever
field the platform's own API exposes (a `language_code`/`locale`-shaped field on the incoming
update/interaction is the common pattern); if the platform exposes none, fall back to a
per-user stored preference (a `locale` column on the `User`/bot-user model) with a `/language`
command to set it, rather than defaulting silently to `fallbackLanguage` forever.

## Review Checklist

- [ ] Every translation key exists in the fallback locale, even if untranslated elsewhere.
- [ ] REST: `AcceptLanguageResolver` used, not raw `HeaderResolver`.
- [ ] Validation messages use `i18nValidationMessage()`, not a hardcoded English string, and
      `I18nValidationExceptionFilter` is wired.
- [ ] Bot: locale resolved from the platform's own per-user locale field, not assumed from
      `Accept-Language` (which a bot update never has).
- [ ] `src/i18n/<locale>/` folders stay one-namespace-per-file, not one giant JSON blob.
